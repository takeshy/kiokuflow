# kiokuflow migration

The service is **kiokuflow** (lowercase), at **https://kiokuflow.net**. Production OAuth/application cutover and the first deployment of the separate GemiHub booking application at **https://gemihub.net** were completed on 2026-11-02. The existing shared VM, notes database, billing identity and original OAuth secrets are retained. GemiHub uses a separate runtime identity and named Firestore database `gemihub`.

Production checks cover public pages, phone/desktop layouts, OAuth authorization URLs, GemiHub Firestore and Vertex AI connectivity, and retirement of the old service worker while preserving IndexedDB and unrelated caches. Actual owner consent, encrypted-note copying and the final move of old settings to Trash require the owner's interactive sign-in and migration start; these have not been performed by deployment.

## Existing data

- New accounts use a `kiokuflow` Drive folder. Sign-in first looks for that folder and then reuses an **accessible** existing `gemihub` folder by ID. This name fallback does not transfer Drive authorization between OAuth projects. Explicit `ROOT_FOLDER_NAME` settings remain authoritative. Do not rename or copy existing folders before choosing the migration method.
- When the original root and file IDs remain accessible, existing settings, RSA identities, encrypted credentials, subscriptions, organization projects and Firestore RAG indexes retain their identifiers. The built-in RAG index is displayed as `kiokuflow`, while its stored key stays `gemihub`. A different root requires a separate data migration; these guarantees do not apply to a newly created workspace.
- Browser caches and login cookies are origin-specific. Before moving from the old site, **Push all local edits on every device**. Sign in again at the new site, then Pull. Existing encryption passwords still unlock the same private keys. Browser-only preferences may need to be set again.
- The extracted Web Builder continues as GemiHub in `../omaiweb` and takes over the old public domain. kiokuflow deployment is scoped to its new domain; legacy browser caches can be recovered separately if needed.
- Existing hosted sites work at `<slug>.gemihub.net` and `<slug>.gemihub.online`; the settings screen advertises `<slug>.kiokuflow.net`. Custom domains stay unchanged. External websites with hard-coded old origins must be updated separately.

## OAuth separation from GemiHub

The extracted Web Builder in `../omaiweb` keeps the **GemiHub** service identity and its existing approved OAuth configuration. kiokuflow removes Google Calendar/Gmail integration and requests only `drive.file` during normal sign-in. Existing GemiHub Google Cloud API enablement and OAuth approval are not revoked by this repository.

The local `.env` is a development credential set. It differs from the original production OAuth credentials referenced by `shared-apps-runtime` in project `geminihub-486523`: Secret Manager `google-client-id` and `google-client-secret` (verified 2026-11-02 without displaying secret values). Reusing that production identity for GemiHub should reference those secrets. kiokuflow uses separate `kiokuflow-google-client-id`, `kiokuflow-google-client-secret` and `kiokuflow-google-picker-api-key` secrets populated from its own local `.env`; existing secrets and IAM bindings are retained. Application environment variable names stay `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_PICKER_API_KEY`.

Non-sensitive `drive.file` avoids sensitive/restricted-scope verification. Brand verification is separate and is needed to display an app name/logo on Google's consent screen. A new unverified brand can use domain-only display where Google's current requirements permit it; do not promise that removing Calendar/Gmail alone eliminates brand review. A separate OAuth project also changes Drive app access: existing app-created files are not automatically granted to a new application. Plan and verify that migration before replacing kiokuflow's production OAuth credentials.

Google sessions and stored background-workflow grants are bound to the current OAuth client. Old browser sessions must sign in again after the cutover. Background workflows pause until the owner has reauthorized and, when applicable, completed migration; an old refresh token is never sent to the new client. OAuth refresh failures use fixed errors so SDK request bodies cannot expose credentials in logs.

### Migration through Settings

On 2026-11-02, the owner confirmed that all observed operations belong to them and authorized the OAuth cutover with a copy-based migration. The new `.env` client belongs to `takeshy-work`; the original production client belongs to `geminihub-486523`.

Existing registered users are automatically directed to **Settings → Bring your existing workspace**, `/settings/migration`, after Google login. The screen announces **kiokuflow.net**, explains the copy, and requires the owner to start it. A settings link allows returning to the page. Japanese/English screens support phone widths.

- Runtime `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_PICKER_API_KEY` reference the three dedicated `kiokuflow-google-*` secrets. Temporary server-only `GOOGLE_MIGRATION_CLIENT_ID` / `GOOGLE_MIGRATION_CLIENT_SECRET` reference the retained old OAuth secrets. Never overwrite or revoke GemiHub's credentials. The `../omaiweb` app serves gemihub.net and detects legacy note settings during its owner login. Its settings notice links to kiokuflow, and shop creation/management remains blocked until its authenticated recheck confirms the old settings have been removed.
- Before rebinding the billing account during login, the server checks that the same Google identity can read legacy settings. Billing-only/stale registrations without those settings are not migration candidates. A Firestore transaction then snapshots the original root and already-encrypted refresh token in `drive-oauth-migrations/{accountId}`. Repeat logins retain the original snapshot. Both Google grants must resolve to the same email, and all operations are bound to the signed-in account and destination root. The source token and upload URLs never appear in responses; upload URLs are encrypted at rest. A failed snapshot blocks account rebinding.
- The owner must **Push all devices first and stop editing both environments during migration**. The owner authorized overwriting existing destination files on 2026-11-02. The tool checks for `settings.json`, enumerates the source recursively, reuses matching destination folders, and overwrites matching files in place using their existing IDs. Other destination files remain. New files get stable IDs, and uploads use bounded 8 MiB resumable chunks. Destination snapshots detect edits after planning. Duplicate source siblings receive stable numbered destination names, such as `opencode (2).md.encrypted`, while keeping their source snapshots and encrypted content unchanged. Existing numbered names are reserved to avoid collisions; duplicate folder children remain separate by source parent ID. Names are stored in the manifest and checked during retries and final verification. Ambiguous destination names and incompatible file/folder or Google-native target types stop planning before writes. Source files are read-only during copying. After destination verification is durably recorded, only the original `settings.json` is moved to Trash, as explicitly requested by the owner. A job lease prevents concurrent copies. Per-file state and fixed target IDs allow resuming after request/server interruption without duplicating completed files.
- Copied files are checked for size and MD5 equality. Before completion, the source inventory is checked again for additions/deletions/changes. Source edits stop completion rather than silently losing changes. At the owner's request, Google-native documents and shortcuts are skipped during planning and final source verification and remain in the original folder. Folders and ordinary notes/attachments still migrate; a planned ordinary file converted to a Google-native type still counts as a source change. Inventories over 20,000 copyable items require separate handling. Failed requests remain resumable; resolve a source change separately rather than treating an old manifest as current.
- Copy requests select up to 24 unfinished manifest entries and run four workers, creating shared ancestors once before their children. Existing `done` flags work without rebuilding an in-progress manifest. Each verified file and its atomic completed-count increment commit in one transaction, checked against the request lease. A 20-second scheduling budget stops new copies from starting; each active file's Drive operations share a 90-second deadline. All started workers settle before the lease is released. Files up to 4 MiB use one bounded read plus one multipart write with source/target MD5 checks; larger files and existing upload sessions retain 8 MiB resumable chunks. Source/destination folder verification is also limited to four concurrent listings. Retryable Drive errors return HTTP 503 with saved progress and a file path when available; the browser retries up to three times with 1/2/4-second waits. Permanent errors and authentication failures stop immediately. Remapped history metadata can be verified again after a lost finalization response.
- Settings retain the RSA identity and encrypted provider credentials; use the **existing decryption password**. History index keys are remapped to new IDs. Old `_sync-meta.json` and `_encrypted-auth.json` are not copied: sync metadata is rebuilt, and external-sync auth is regenerated with the new client-bound refresh token. The preserved source refresh token is removed from the migration document after successful completion. Cleanup has its own durable verified checkpoint: a lost response after moving the old settings to Trash can be retried without copying/deleting more data. GemiHub then rechecks the absence of legacy settings before enabling shop creation.
- New file/root IDs require rebuilding RAG indexes and checking public links, old file references embedded in history, and external sync connections. RAG configuration remains, but old index handles/file mappings are cleared. File bodies and encrypted histories are not rewritten. Registration/billing account identity stays unchanged, while its root and refresh token are rebound at login.

A raw Drive folder ZIP remains a backup, not a complete account migration. The regular visible-tree ZIP export can omit system files or failed downloads. If importing content manually, use the **kiokuflow file-tree import**, rather than uploading through Drive's own UI; never restore an old `_sync-meta.json` registry into the new root. Registration records also exclude some free Drive-only users, so workspace hashes alone are not a count of people.

## Deployment sequence

1. `kiokuflow.net` is registered with Cloudflare Registrar, so its authoritative nameservers stay at Cloudflare. `branding.auto.tfvars` sets `domain = "kiokuflow.net"`, `legacy_app_domain = "gemihub.net"` and `manage_rebrand_dns = false`. Do not disable the module-wide `manage_dns`: the old domain's Cloud DNS zone and certificates must stay managed. The new domain gets additive DNS authorization, apex/wildcard certificates and certificate-map entries; its DNS records are created in Cloudflare. Existing IP, backends, VM, buckets and databases retain their identities. Review the production plan before applying; do not replace these resources unexpectedly.
2. In Cloudflare **kiokuflow.net → DNS → Records**, add `A @` and `A *` pointing to the existing load-balancer IP (`34.120.253.130`, confirmed 2026-11-02); use **DNS only** (gray cloud), TTL Auto. Prepare the new Certificate Manager DNS authorization/certificates/map entries after reviewing the plan. Publish the exact CNAME returned by `terraform -chdir=terraform/environments/prod output -json rebrand_dns_authorization` in Cloudflare, also **DNS only**, and retain it for automatic renewal. Wait for both certificates to become ACTIVE before application cutover. With external DNS, `nameservers` is empty; `legacy_nameservers` still reports the retained old zone. If Google site verification is required, add the new domain's verification TXT in Cloudflare rather than reusing the old token. A records alone do not make the new application ready.
3. Use the **separate kiokuflow OAuth project/client** with callback `https://kiokuflow.net/auth/google/callback` and website origin `https://kiokuflow.net`. Leave GemiHub's existing brand, client and callback registrations unchanged. kiokuflow requests only `drive.file`; brand verification remains separate from scope verification. Publish the new-domain homepage/privacy policy, configure its authorized domain, and use a Picker API key from the same project. Its referrers include the website and `https://docs.google.com/*`, with Picker/Drive API restrictions.
4. Deploy the application with `KIOKUFLOW_MAIN_DOMAIN=kiokuflow.net`. For the shared VM, update its actual runtime environment/secrets separately (Cloud Run variables do not configure the shared VM). Keep the deployment group `gemihub` and current GCP resources. Set `BLUESKY_PUBLIC_URL=https://kiokuflow.net` where Bluesky is enabled; update external OAuth/MCP client registrations and Stripe return URLs or webhook endpoints that use the old origin. The production scheduler URL/audience and existing Stripe webhook URL now use kiokuflow.net; its signing secret is unchanged. Reconnect external sync clients to the new workspace rather than relying on old-domain API paths.
5. Verify login/logout, Drive root-folder reuse, decryption, Push/Pull, paid RAG, Gemini/OpenAI Live, hosted slug/custom-domain sites, public file links, scheduled jobs and external Drive-sync clients on the deployed environment. Check Japanese/English pages and phones. Local automated tests do not establish deployed or authenticated end-to-end success.
6. The old domain belongs to the extracted GemiHub application, deployed as `gemihub-web` on port 8105. Its apex and `*.shops.gemihub.net` routes have their own backend; kiokuflow retains the original `gemihub` runtime on port 8101. GemiHub serves a no-store retirement worker at `/sw.js` which removes only old `gemihub-sw-` caches and unregisters itself. It never deletes IndexedDB. The old notes UI and its API paths are no longer served on that origin; `?legacy=1` does not reopen them through GemiHub. Unsynced browser-only content is outside the server Drive-copy operation, so retain that browser's data for recovery. Original DNS/certificates and OAuth secrets remain managed for GemiHub.
7. The GitHub repository is `takeshy/kiokuflow`. Its existing Cloud Build deployment trigger must reference the renamed repository through the corresponding Cloud Build v2 connection; a stale `takeshy/gemihub` repository reference can miss push events even though Git cloning follows GitHub's redirect. GemiHub has its own `takeshy/omaiweb` connection and deployment trigger. Persist the current shared-VM runtime manifest after deploying, and retain the private shared-VM variable file in its existing versioned GCS location.

## Shared VM disk recovery (2026-11-06)

The shared VM's 30 GB root disk filled with unused deployment images. Nginx
logged `No space left on device`; requests requiring a buffered upload could
not reach the application. Removing unused images older than 24 hours
reclaimed 15.05 GB. Running containers and their data were retained.
The user confirmed that both mobile Drive Push and chat worked again after
the cleanup. The root filesystem then had about 16 GB free (44% used).

`scripts/ops/shared-apps-image-gc.service` and its `.timer` run that cleanup
hourly. Install both units under `/etc/systemd/system/`, run
`systemctl daemon-reload`, then
`systemctl enable --now shared-apps-image-gc.timer`. The service uses
`/opt/shared-apps/deploy.lock`, matching the shared deployment script, and
skips a run while a deployment holds it. Docker retains images referenced by
containers; unused images less than 24 hours old also remain. Older rollback
images can be pulled again from Artifact Registry. No volumes are pruned.
Reinstall these units if the VM is rebuilt; they are not part of the shared
VM's bootstrap bundle.

## Compatibility names retained

`GEMIHUB_MAIN_DOMAIN` and `GEMIHUB_OKF_*` remain fallback environment aliases; new configurations should use `KIOKUFLOW_MAIN_DOMAIN` and `KIOKUFLOW_OKF_*`. The current brand defaults to `kiokuflow.net` if neither domain variable is set.

Published applications can use `window.kiokuflow`; `window.gemihub` is the same SDK object. Existing `/__gemihub/*` routes, `web/__gemihub/` mock/schema files, `/api/okf/gemihub`, `gemihub-okf` distribution paths, `gemihub-command` workflow nodes, browser storage keys and Firestore index keys remain compatible. Both current and old OKF manifests are accepted.

The application repository is now [takeshy/kiokuflow](https://github.com/takeshy/kiokuflow). Existing local checkouts can update their remote with `git remote set-url origin git@github.com:takeshy/kiokuflow.git`; the checkout directory can retain its existing name.

The `gemihub-sync-core` dependency, the separately released **GemiHub - Drive Sync** Obsidian plugin and **GemiHub Desktop** keep their actual names and URLs. This repository does not rename or publish those external products. Historical screenshot filenames and internal API/type names are also stable; user-facing labels use the new service name.

## DNS provider references

- [Cloudflare Registrar nameserver restriction](https://developers.cloudflare.com/registrar/get-started/register-domain/): domains registered there keep Cloudflare nameservers.
- [Google Certificate Manager DNS authorization](https://docs.cloud.google.com/certificate-manager/docs/dns-authorizations): publish the returned CNAME at the authoritative DNS provider.
- [Cloudflare proxy status](https://developers.cloudflare.com/dns/proxy-status/): use DNS only for initial routing and certificate verification.

- [Changes to an approved OAuth app](https://support.google.com/cloud/answer/13464018): name, redirect and branding changes require brand re-verification; unchanged scopes need no additional justification.
- [Brand verification and pending reviews](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification): check the existing review before editing branding or cancelling verification.
